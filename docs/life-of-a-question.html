neo · question pipeline

Life of a question

Everything that happens between pressing Ask and reading the answer, step by step, in plain words. The example throughout is a real run on your data (jp_morgan.csv, 955 rows): “How many failed-bank deals happened in the 1980s?”, asked as Admin.

132failed-bank deals in the 1980s
955deals in jp_morgan.csv
ProvedZ3, then Lean re-checked it
4 of 4requirements met by the model
Every claimin the answer checked

The one idea

The language model never calculates anything. Its job is to rewrite your question as a precise model: a short recipe that says which rows to use and which formula to apply, written in the ontology's own names. Code checks the recipe. The data lake computes it with exact whole numbers. Z3 proves the result is the only one possible, and Lean checks Z3's work. A second, separate LLM writes down what the question requires, and code checks the model against each requirement. At the end an LLM writes the answer in words, and code checks every number and claim in it before you see it.

Code

neo's own program. The same input always gives the same output.

LLM

Claude, in three separate jobs: lists the question's requirements, writes the model, writes the answer. Never sees data rows, and every claim it makes is checked.

Data lake

DuckDB over a frozen copy of your one table: jp_morgan.csv, 955 deals. Every number is calculated here.

Z3

A solver. Proves an answer is the only possible one, finds best values and clashes.

Lean

A proof checker with a small trusted core. Re-checks what Z3 decided, and every small claim: rounding, comparisons, filters.

Phase 1

Understand the question

No AI is involved yet. neo freezes the data, finds what your words mean, and decides what the LLM is allowed to know.

1

Freeze the data and the meaning

Code

Before anything runs, neo takes a picture of the data and of the ontology, so the whole answer uses one consistent version of both.

  • Checks who is asking. There is one user, Admin: the highest clearance (restricted), no row limits, can approve reviews, and has no query size limit.
  • Freezes the data. It records the exact version of every table, called the snapshot. Data loaded a second later is not seen by this run.
  • Freezes the meaning. It records the ontology version and a fingerprint of each approved rule.
  • Starts the record. It creates a run id and writes “question asked” to the audit log.
In the example
Runrun_20261105105653_94112983
Data snapshotsnap_6044484e82ce6e90
Ontology versionv0003-ddf412f2

Why it matters: replaying this run next year gives the same answer, because every later step reloads exactly this snapshot and this ontology version.

Saved: the run record and var/audit.jsonl.

2

Link your words to the ontology

Code

neo looks up the words of your question in the ontology, the company's dictionary of what the data means.

  • Splits the question into words. Lowercase, punctuation removed, simple plurals reduced (“deals” becomes “deal”).
  • Exact phrases. Every run of 1 to 6 words is compared with the names and aliases of terms, tables, columns, metrics and history windows. Longer matches score higher: 0.6 plus 0.15 per word, up to 1.0.
  • Similar wording. The question is also compared with each object's description, so different wording still finds the right thing. These matches score lower and are kept only above a threshold.
  • Unknown words are saved as suggestions for new aliases.
In the example
Your wordsOntology objectKindScore
“failed bank”term_failed_bank_dealbusiness term0.90
“deals”dealentity (table)0.75
“deal”term_acquired_bankbusiness term (alias)0.75
“deal”target_name, target_certcolumns (through their term)0.75
similar wordingis_assisted_failedcolumn (a formula)0.56
similar wordingterm_deal_categorybusiness term0.37

“happened” matched nothing and was saved as an alias suggestion.

If nothing matches, neo stops here and asks which table you mean (status needs_clarification). The LLM is never asked to guess.

Saved: steps/retrieve.json.

3

Build the briefing

Code

neo picks the tables the question is about and writes a short briefing for the LLM: only the part of the ontology this question needs.

  • Chooses tables. Each matched word votes for its table. Tables with at least a quarter of the top score are kept (up to 4), plus tables one join away.
  • Applies access. Columns above the user's clearance are left out and counted. Row limits for the user are noted. Admin sees every column and every row.
  • Gathers context. For each table: columns with unit and meaning, the exact category values read from the data, joins and whether they repeat rows, approved metrics, history windows, business rules (constraints), terms and approved legal rules.
  • Writes it as text. This briefing is everything the LLM learns about your data. It contains no data rows.
In the example

Main table deal, the only table. 0 columns hidden. 7 constraints from your ontology. An excerpt of what the LLM reads:

- entity `deal`: Deal (bank that ended up in JPMorgan Chase). One row per target bank; key `target_cert`;
  time field effective_date. 955 banks that ended up inside JPMorgan Chase, 1970-2023 (FDIC BankFind).
    year [term_deal_year]: number, years | bigint, filled 100%, range 1970 to 2023
    deal_category [term_deal_category]: text | values: 'Voluntary M&A' (717); 'Assisted / failed-bank deal' (238)
    is_assisted_failed: bool = deal_category == 'Assisted / failed-bank deal'
## Constraints (`block` ones must be addressed in grounding when they apply)
- con_failed_bank_definition [block, enum_semantics] on term_failed_bank_deal: Failed-bank / FDIC-assisted
  deals are the 238 rows with deal category 'Assisted / failed-bank deal' ...

Saved: the briefing text, in steps/retrieve.json.

4

List the requirements

LLMnew

A second, separate LLM job reads only your question and the briefing, and writes down what any correct answer must respect. It never sees the model that will answer the question.

  • Small typed claims, each one checkable by a program: whose rows (universe), which conditions the rows must meet (filters), what is computed (measure), one result per what (group), and any ranking (order).
  • Written in the model language, so code can run them: a filter is a real condition such as year >= 1980 and year < 1990.
  • Kept apart on purpose. If the model writer misreads your question, this writer, working alone, is unlikely to misread it the same way. The web page shows the list as “I understood the question as”, so you can correct it.
In the example
IdKindRequirementAs code
R1universethe rows are dealsentity deal
R2filteronly failed-bank dealsdeal_category == 'Assisted / failed-bank deal'
R3filterin the 1980syear >= 1980 and year < 1990
R4measurethe answer is a countcount

Note that R2 and R3 are written differently from the model in step 5. That is the point: the check in step 12 proves they mean the same rows.

If no LLM is configured for this job (llm.tasks.requirements), the step is skipped and the claim ledger says the meaning was not checked.

Saved: steps/requirements.json.

Phase 2

Turn it into a precise model

The only creative step. The LLM writes the recipe; code checks every part of it before a single query runs.

5

Write the model

LLM

Claude rewrites the question as a small, precise model: which rows, which formula, and which kind of answer. For a question with several parts it writes a plan: one small model per part, combined at the end.

  • What Claude receives: its role (“you never compute answers and never see raw data”), the manual on writing models, the list of allowed functions, the briefing, and your question.
  • Checks before sending: the request must contain no data rows; the user's daily token budget (2,000,000 for Admin) must not be used up. Rate-limit errors are retried. Every call is logged with its token count and time.
  • What comes back: a JSON model. Its form says what kind of answer this is: a number (value), a table, a top or bottom item (extremum), a list (set), a yes/no check, “is this possible?” (feasibility), “what is the best value?” (optimisation), several parts combined (plan), or “the data cannot answer this”.
  • Grounding: the model also lists the business terms it relied on and how it handled each enforced rule.
In the example 
{ "form": "value",
  "interpretation": "Count of deals that were assisted or failed-bank deals with year 1980 to 1989.",
  "universe": {"entity": "deal"},
  "rows": "is_assisted_failed and 1980 <= year <= 1989",
  "target": {"expr": "count()"},
  "grounding": {"terms": ["term_deal_category", "term_deal_year"],
    "constraints_applied": [{"id": "con_failed_bank_definition",
                             "how": "counted with deal_category, not the failure_* columns"}]} }

In plain words: take the deals table, keep the rows that are failed-bank deals with a year from 1980 to 1989, and count them. is_assisted_failed is a formula in the ontology (deal_category == 'Assisted / failed-bank deal'), so the model never types the category text itself.

Saved: attempts/attempt_1.json, and the LLM call in the call log.

6

Check the model

Code

Before any query runs, neo checks the model against the ontology and the user's rights, and collects every problem, not just the first.

CheckWhat it stops
Real namesA table, column or join that does not exist (“did you mean branches_transferred?”)
AccessUsing a column or table above the user's clearance
UnitsAdding thousands to dollars, or a percent to a ratio, without converting
TimeAdding a balance (a level on a date) to an amount over a period; using a year-to-date figure as one month
Double countingSumming the “one” side of a one-to-many join, which would count it many times
Row limitsAdded by code to every query; the LLM cannot remove them (Admin has none)
RulesCiting a rule that is not approved or not in force
GroundingIgnoring an enforced (block) constraint. One applies when a trigger word is in the question or the model reads a column it covers; it must be marked applied (with how) or not applicable (with why)
SizeScanning over 50 million rows without permission for large queries (Admin has it)
In the example

Passed on the first attempt. One enforced rule from your ontology applied: con_failed_bank_definition, because the question says “failed bank”. The model marked it applied (“counted with deal_category, not the failure_* columns”). Without that line, the model would have been sent back.

If it fails: the full list of errors goes back to Claude with “The model was rejected. Fix every problem below.” Claude gets up to 3 fixes (4 attempts in all). Problems found while compiling or proving (steps 7 to 9), and requirements the model does not meet (step 12), go back the same way. If it still fails, the status is no_model and you see the last problems. No answer is invented.

Phase 3

Compute and prove

The lake calculates, Z3 proves, Lean checks Z3, and a second program recomputes the answer. All four must agree.

7

Compile to exact SQL

Code

The model becomes SQL, written so that no number is ever rounded.

  • Real tables: table names come from the ontology and point at the frozen snapshot, not the live table.
  • Fractions, not decimals: every number is kept as a pair of whole numbers, top and bottom of a fraction. A decimal like 0.012345 becomes 12345 / 1000000.
  • No division in comparisons: a/b > c/d is decided by comparing whole-number products, so nothing is rounded.
  • Big integers: totals use 128-bit whole numbers. If a number would overflow, the query stops with an error instead of rounding.
  • Missing values are counted and reported, never silently treated as zero.
  • Joins come from ontology relations, and any row limits go into every WHERE.
In the example 
SELECT COUNT(*)                                                   -- the number of deals
FROM s_6044484e82ce6e90."deals" t0                                -- the frozen snapshot
WHERE COALESCE(t0."deal_category" = 'Assisted / failed-bank deal' -- is_assisted_failed, from the ontology
           AND 1980 - t0."year" <= 0                             -- 1980 <= year, written as a difference
           AND t0."year" - 1989 <= 0, FALSE)                     -- year <= 1989
8

Compute in the lake

Data lake

DuckDB runs the SQL inside the data lake. This is where every number in the answer is calculated.

  • Counts first: how many rows the user can see, and how many pass the filter.
  • Then the totals, all in one pass over the data.
  • Then evidence: 8 example rows for people to look at. They are marked as row data and never sent to the LLM.

9

Prove with Z3

Z3

Z3 checks that the answer is the only value possible. How it does that depends on the kind of question.

  • A number: Z3 is told “answer = the exact number from the lake”, then asked “could the answer be anything else?”. It replies unsat, meaning impossible. That is the proof.
  • A table: each cell is proved the same way.
  • Top or bottom: for each rank, a query counts the rows strictly better. The count must match the candidates, so nothing outside the ranking beats it.
  • A yes/no claim about rows: a query searches every row for one that breaks the claim. None found means it holds on this snapshot.
  • Questions with unknowns (“what is the best value?”, “is this possible?”): Z3 solves for the unknowns, with one rule per row. Up to 5,000 rows it sees every row at once; above that it works in rounds (refinement). Your table has 955 rows, so Z3 always sees every row.
  • A plan: each part is a number, proved as above on its own; then the parts are combined with exact fractions and Z3 proves each combined value.
In the example 
(declare-fun ans () Real)            ; an unknown called ans
(assert (= ans (to_real 132)))       ; ans equals the lake's count
(assert (distinct (to_real 132) ans)) ; ...and ans is something else?
→ unsat: no other value is possible
A question with two parts: a plan

“Were failed-bank targets in Texas in the 1980s bigger on average than voluntary ones?” The model is a plan with two small parts and one combination:

PartWhat it computesRowsProved value
N1average pre-deal assets, Texas failed-bank targets, 1980–1989, blanks left out79$425.899177 million
N2the same for voluntary targets125$122.942944 million
failed_biggerN1 > N2true
ratioN1 / N23.464202

Each part was proved and recomputed on its own, so a mistake in one part would be reported for that part only. The exact values are fractions: N1 = 6729207 / 15800 and N2 = 3841967 / 31250.

10

Re-check with Lean

Lean

Z3 is fast, but its “unsat” has to be trusted. Lean, a proof checker with a small trusted core, re-checks what Z3 decided using exactly the same formulas.

  • neo writes Z3's conclusions as Lean theorems in a new file for this run.
  • Facts about numbers are checked by Lean's core recomputing the exact fractions itself (decide +kernel). If Lean disagrees with Z3, the run goes to human review.
  • Facts “for every value”, such as “no larger cut is allowed”, are proved by Lean's automatic prover (grind) from only the rows that decide the answer.
  • General theorems in lean/Neo, proved once for all runs (38 of them), explain why a result checked on some rows holds for every row, why a rounded number is honest, and why proved parts give the combined value.
In the example

1 theorem: 132 is exactly what the lake's count gives. checked in 2.1 s. It relies on the library theorems unique_of_unsat, sum_const_den and cmp_sign.

For the Texas plan, Lean checked the two parts' values and the combination: given N1 and N2, “N1 > N2” and the ratio 3.464202… follow exactly (library theorem Neo.Compose.combine_value).

If Lean is not installed, or lean.enabled is off, this step is skipped and the certificate does not mention it.

11

Recompute another way

Code

A second, separate program recomputes the answer from the raw columns, without the SQL compiler. The two results must agree.

  • Up to 300,000 rows: Python reads the raw columns of the same snapshot and evaluates the model with exact fractions.
  • Above that: a separate floating-point SQL version is used. It is approximate, and the certificate says so.
  • If they disagree, the status becomes mismatch: the answer is marked NOT proved and sent to human review.
In the example

Exact recomputation over the 955 deals. matched

12

Check the meaning

Data lakeZ3new

Steps 7 to 11 prove the answer is right for the model. This step checks that the model means what you asked, by testing it against each requirement from step 4.

  • Filters, on the real rows: the lake counts rows the model keeps that a requirement excludes. It must be 0, or the model answers about rows you did not ask about.
  • Nothing left out: the lake also counts rows your question includes that the model drops. That is allowed only when each such row is missing a value the model needs (for example a blank pre-deal size), and the ledger says so.
  • Filters, for every possible row: Z3 tries to prove “model's filter → requirement” for any values at all, not only today's data. When it does, the statement becomes a small Lean theorem, checked in step 17.
  • Universe, measure, grouping, ranking: compared with the model's structure (a count must be a count, “per state” must be grouped by state).
In the example
RequirementCheckRows that break itResult
R1 dealsthe model's universe—matched
R2 failed-bank onlylake count, then Z3: model → R2 for every row0matched
R3 1980slake count, then Z3: model → R3 for every row0matched
R4 a countthe model's target—matched
R2 + R3 togetherrows the question includes that the model drops0matched

The model wrote is_assisted_failed and 1980 <= year <= 1989; the requirements said deal_category == '…' and year < 1990. Z3 expanded the ontology formula and proved the model never keeps a row the requirements exclude.

If it fails: “the model is valid but does not answer the question as asked” goes back to the model writer with each unmet requirement and the row count, and the model is fixed like any other error. If the last attempt still fails, the answer is kept but sent to human review.

Phase 4

Explain and deliver

The LLM double-checks its own reading of the question, code writes down the facts, and the LLM turns those facts into an answer.

13

Review the model

LLM

Claude re-reads its model next to a summary of the result, and either approves it or proposes a fix.

  • What Claude sees: its model and a summary (the answer, row counts, checks). No rows, and no Z3 or Lean files.
  • What it asks itself: Is this the exact question? The right columns for each term? Units converted? No double counting? Is the result plausible? A zero, for example, may mean a misspelled category.
  • Its reply: “ok”, or “revise” with a corrected model. A revised model goes through steps 6 to 12 again, and replaces the original only if it passes, requirements included.
In the example

Verdict: ok.

Saved: steps/review.json.

14

Write the certificate

Code

Code writes the proof certificate: the complete record of what was asked, how it was computed and how it was proved.

  • The question, the interpretation, the form, the status, and how many rows were used out of how many visible.
  • The result and its exact values.
  • The model: table, joins, filters, definitions, and which numbers were stated rather than taken from data.
  • Each rule applied or not applicable, with the reason.
  • Every check and its result, including Z3, Lean and the independent recomputation.
  • Each requirement from step 4 and whether the model met it (step 12).
  • The values the answer may cite, by name, for the slots in step 15.
  • Caveats: missing values skipped, row limits applied, approximations.
  • Where it came from: snapshot, ontology version, rules cited, the LLM used, the user and the run id.

Two copies are made: the full one for people, and one for the LLM with row-level evidence removed.

Saved: certificate.md.

15

Write the answer

LLM

Claude writes the answer for a business reader, using only facts from the certificate, and writes numbers as slots that code fills in.

  • Slots, not typed digits: Claude writes {{answer}} or {{N1|raw|1}}; code fills each one from the exact proved value, in the unit asked. A copied number cannot be wrong.
  • A list of claims: next to the text, Claude lists every claim it makes: numbers, comparisons (“bigger than”), values it worked out, which rows the answer covers, caveats, and anything that is an opinion.
  • Sections: the answer, how it was worked out, what was proved, and caveats. Every caveat the ontology requires for this question is listed for Claude to include.
In the example 
"**{{answer}} failed-bank deals** took effect from 1980 to 1989, out of {{universe_rows}} deals …"
→ "**132 failed-bank deals** took effect from 1980 to 1989, out of 955 deals in the file (… about 13.8%)."

No API key was set for this run, so the answer text was scripted; every step that checks it ran for real.

Saved: steps/answer.json, with every draft.

16

Check the answer

Codenew

Before you read a word, code checks every claim in the answer. Wrong claims go back to Claude; what still fails is removed.

Kind of claimHow it is checked
A number in a slotFilled from the proved value, so it is right by construction
Any other numberFound by a scan of the whole text, so an unlisted claim is still caught. It must be a proved value at the precision shown (units converted), one proved number as a share of another, a number in the certificate, or a number from your question
A comparisonRecomputed exactly on the proved values
A worked-out valueThe arithmetic is redone with exact fractions, and the rounding checked
Which rows it coversMust cite requirements that step 12 matched
A caveat the ontology requiresMust be there; if still missing after the repairs, code adds it from the ontology's own text
A new fact, an opinionA fact not in the certificate is unsupported; an opinion is labelled as not checkable
  • Repairs: the problems go back to Claude with the exact reason, for example “A1 says 123, the proved value is 132” (up to 2 fixes).
  • Then removal: a sentence with a claim that still fails is removed, and the answer says how many sentences were removed. The run goes to review.
In the example

Every claim passed: the slots 132 and 955; the years 1980 and 1989 (from the model); 13.8% recomputed as 132 / 955 = 0.13822; and the scope claim, citing R2 and R3, which step 12 matched.

In the Texas plan, the ontology's caveat con_pre_deal_coverage (pre-deal assets are missing for 145 rows) applies because the model reads pre-deal assets. The scripted answer left it out, so code added it from the ontology's text.

17

Claim ledger

CodeLeannew

One table of every claim in the run: who made it, what checked it, and the result. Lean then checks the small claim theorems.

  • From the question: each requirement and whether the model met it.
  • From the model: each result, or each part of a plan, with its proof status.
  • From the answer: each claim and its check.
  • One small theorem per claim: “the shown 132 is the exact value” (rounds_*), “13.8% is 132 / 955, rounded honestly” (derived_*), “the model keeps only rows that meet R2” (fidelity_R2). Lean's kernel checks them all in one run.
In the example

16 rows in the ledger, all passed. Lean checked 7 claim theorems in 2.7 s: 2 about the meaning (R2, R3), 4 about rounding, and 1 about the derived percentage. The ledger is added to the certificate.

Saved: steps/ledger.json, and the ledger at the end of certificate.md.

18

Route for review

Code

Code decides whether a person must look at the answer before it is trusted.

A run goes to the review queue when any of these is true:

  • The status is not a proof (failed, mismatch, not unique, and so on).
  • The independent check disagreed, or was only approximate.
  • Some totals were computed in floating point.
  • Lean rejected a fact that Z3 reported.
  • A backtest contradicts real past events.
  • The table belongs to a high-impact area (regulatory, board).
  • 4 or more enforced rules shaped the model.
  • The model still does not meet a requirement after the repairs (step 12).
  • The answer check had to remove a claim, or Lean rejected a claim theorem (steps 16 and 17).
In the example

No reasons, so the answer was delivered straight away. Admin is the only user who can approve reviews.

Save and audit

Code

Everything is written to disk, so the run can be inspected, replayed and audited later.

  • Replay on today's data: the same model on the latest data and ontology.
  • Feedback: a thumbs up or down with a comment, stored with the run.

How a run can end

StatusWhat it means
provedA number, table, ranking or list, proved and independently matched
optimalThe best value was found, nothing better is allowed, and it is reachable
feasible infeasibleIt is possible (with an example), or impossible (with the rules that clash)
refutedA claim was checked and is false, with counterexamples
unboundedThere is no best value: it can grow without limit
undefinedNo eligible row had a value
not_expressibleThe data cannot answer this, and the LLM says so
needs_clarificationThe question could not be linked to any table (step 2)
needs_approvalThe query is too large for the user (step 6)
mismatchThe independent recomputation disagreed: not proved, sent for review
no_modelNo valid model after 4 attempts, so no answer is given
llm_errorThe language model could not be reached or failed
Reference

Words used here

Ontology
The company's dictionary of its data: what each table and column means, in which unit, and which rules apply.
Term
A business word with a definition, such as failed-bank deal or deal year. Columns are linked to terms.
Entity
A kind of thing with its own table. Here there is one: a deal, one row per bank that ended up inside JPMorgan Chase (jp_morgan.csv).
Constraint
A business rule in the ontology. “Block” rules must be addressed by the model; “info” rules are background.
Snapshot
A frozen version of every table, so a run always reads the same data.
Briefing
The short extract of the ontology the LLM reads for one question. It has no data rows.
Model
The LLM's precise version of the question: which rows, which formula, which kind of answer.
Form
The kind of answer: value, table, extremum, set, check, feasibility, optimisation, plan, or not expressible.
Requirement
A small, checkable statement of what the question needs, written by a separate LLM that never sees the model.
Fidelity check
Testing the model against each requirement, on the real rows and, with Z3, for every possible row.
Slot
A placeholder like {{answer}} in the answer text, filled by code from the exact proved value.
Claim ledger
The table of every claim in a run, who made it, what checked it, and the result.
Grounding
The part of the model that cites the terms used and says how each enforced rule was handled.
Row limit (row policy)
A filter added by code for users who may see only some rows. Admin has none.
Exact fraction
A number kept as a whole-number top and bottom, so nothing is ever rounded.
Z3
A solver. “Unsat” means no value can satisfy what it was asked, which is how a proof is phrased.
Refinement
Solving on a small set of rows, checking the result against every row in the lake, adding the rows that break it, and repeating.
Lean
A proof checker. Its small core re-checks Z3's conclusions; a library of general theorems covers the step from some rows to every row.
Certificate
The code-written record of the question, model, result, checks and sources. The final answer may use only these facts.
