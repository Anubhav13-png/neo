neo · question pipeline

Life of a question

Everything that happens between pressing Ask and reading the answer, step by step, in plain words. The example throughout is a real run on your data: “How many failed-bank deals happened in the 1980s?”, asked as Admin.

132failed-bank deals in the 1980s
955deals in jp_morgan.csv
ProvedZ3, then Lean re-checked it
Matchedindependent recomputation
2.0 sfrom Ask to answer

The one idea

The language model never calculates anything. Its job is to rewrite your question as a precise model: a short recipe that says which rows to use and which formula to apply, written in the ontology's own names. Code checks the recipe. The data lake computes it with exact whole numbers. Z3 proves the result is the only one possible, and Lean checks Z3's work. At the end the model writes the answer in words, using only facts that code wrote down.

Code

neo's own program. The same input always gives the same output.

LLM

Claude. Writes the model, reviews it, writes the final text. Never sees data rows.

Data lake

DuckDB over a frozen copy of your two tables: the deals CSV and FDIC history. Every number is calculated here.

Z3

A solver. Proves an answer is the only possible one, finds best values and clashes.

Lean

A proof checker with a small trusted core. Re-checks what Z3 decided.

Phase 1

Understand the question

No AI is involved yet. neo freezes the data, finds what your words mean, and decides what the LLM is allowed to know.

1

Freeze the data and the meaning

Code

Before anything runs, neo takes a picture of the data and of the ontology, so the whole answer uses one consistent version of both.

  • Checks who is asking. There is one user, Admin: the highest clearance (restricted), no row limits, can approve reviews, and has no query size limit.
  • Freezes the data. It records the exact version of every table, called the snapshot. Data loaded a second later is not seen by this run.
  • Freezes the meaning. It records the ontology version and a fingerprint of each approved rule.
  • Starts the record. It creates a run id and writes “question asked” to the audit log.
In the example
Runrun_20261103191750_8edc80a0
Data snapshotsnap_4a1cb2ceb8871c88
Ontology versionv0002-0b6222eb

Why it matters: replaying this run next year gives the same answer, because every later step reloads exactly this snapshot and this ontology version.

Saved: the run record and var/audit.jsonl.

2

Link your words to the ontology

Code

neo looks up the words of your question in the ontology, the company's dictionary of what the data means.

  • Splits the question into words. Lowercase, punctuation removed, simple plurals reduced (“deals” becomes “deal”).
  • Exact phrases. Every run of 1 to 6 words is compared with the names and aliases of terms, tables, columns, metrics and history windows. Longer matches score higher: 0.6 plus 0.15 per word, up to 1.0.
  • Similar wording. The question is also compared with each object's description, so different wording still finds the right thing. These matches score lower and are kept only above a threshold.
  • Unknown words are saved as suggestions for new aliases.
In the example

If nothing matches, neo stops here and asks which table you mean (status needs_clarification). The LLM is never asked to guess.

Saved: steps/retrieve.json.

3

Build the briefing

Code

neo picks the tables the question is about and writes a short briefing for the LLM: only the part of the ontology this question needs.

  • Chooses tables. Each matched word votes for its table. Tables with at least a quarter of the top score are kept (up to 4), plus tables one join away.
  • Applies access. Columns above the user's clearance are left out and counted. Row limits for the user are noted. Admin sees every column and every row.
  • Gathers context. For each table: columns with unit and meaning, the exact category values read from the data, joins and whether they repeat rows, approved metrics, history windows, business rules (constraints), terms and approved legal rules.
  • Writes it as text. This briefing is everything the LLM learns about your data. It contains no data rows.
In the example

Phase 2

Turn it into a precise model

The only creative step. The LLM writes the recipe; code checks every part of it before a single query runs.

4

Write the model

LLM

Claude rewrites the question as a small, precise model: which rows, which formula, and which kind of answer.

  • What Claude receives: its role (“you never compute answers and never see raw data”), the manual on writing models, the list of allowed functions, the briefing, and your question.
  • Checks before sending: the request must contain no data rows; the user's daily token budget (2,000,000 for Admin) must not be used up. Rate-limit errors are retried. Every call is logged with its token count and time.
  • What comes back: a JSON model. Its form says what kind of answer this is: a number (value), a table, a top or bottom item (extremum), a list (set), a yes/no check, “is this possible?” (feasibility), “what is the best value?” (optimisation), or “the data cannot answer this”.
  • Grounding: the model also lists the business terms it relied on and how it handled each enforced rule.
In the example 
{ "form": "value",
  "interpretation": "Count of deals that were assisted or failed-bank deals with year 1980 to 1989.",
  "universe": {"entity": "deal"},
  "rows": "is_assisted_failed and 1980 <= year <= 1989",
  "target": {"expr": "count()"},
  "grounding": {"terms": ["term_deal_category", "term_deal_year"],
    "constraints_applied": [{"id": "con_failed_bank_definition",
                             "how": "counted with deal_category, not the failure_* columns"}]} }

In plain words: take the deals table, keep the rows that are failed-bank deals with a year from 1980 to 1989, and count them. is_assisted_failed is a formula in the ontology (deal_category == 'Assisted / failed-bank deal'), so the model never types the category text itself.

Saved: attempts/attempt_1.json, and the LLM call in the call log.

5

Check the model

Code

Before any query runs, neo checks the model against the ontology and the user's rights, and collects every problem, not just the first.

CheckWhat it stops
Real namesA table, column or join that does not exist (“did you mean branches_transferred?”)
AccessUsing a column or table above the user's clearance
UnitsAdding thousands to dollars, or a percent to a ratio, without converting
TimeAdding a balance (a level on a date) to an amount over a period; using a year-to-date figure as one month
Double countingSumming the “one” side of a one-to-many join, which would count it many times
Row limitsAdded by code to every query; the LLM cannot remove them (Admin has none)
RulesCiting a rule that is not approved or not in force
GroundingIgnoring an enforced (block) constraint. One applies when a trigger word is in the question or the model reads a column it covers; it must be marked applied (with how) or not applicable (with why)
SizeScanning over 50 million rows without permission for large queries (Admin has it)
In the example

Passed on the first attempt. One enforced rule from your ontology applied: con_failed_bank_definition, because the question says “failed bank”. The model marked it applied (“counted with deal_category, not the failure_* columns”). Without that line, the model would have been sent back.

If it fails: the full list of errors goes back to Claude with “The model was rejected. Fix every problem below.” Claude gets up to 3 fixes (4 attempts in all). Problems found while compiling or proving (steps 6 to 8) go back the same way. If it still fails, the status is no_model and you see the last problems. No answer is invented.

Phase 3

Compute and prove

The lake calculates, Z3 proves, Lean checks Z3, and a second program recomputes the answer. All four must agree.

6

Compile to exact SQL

Code

The model becomes SQL, written so that no number is ever rounded.

  • Real tables: table names come from the ontology and point at the frozen snapshot, not the live table.
  • Fractions, not decimals: every number is kept as a pair of whole numbers, top and bottom of a fraction. A decimal like 0.012345 becomes 12345 / 1000000.
  • No division in comparisons: a/b > c/d is decided by comparing whole-number products, so nothing is rounded.
  • Big integers: totals use 128-bit whole numbers. If a number would overflow, the query stops with an error instead of rounding.
  • Missing values are counted and reported, never silently treated as zero.
  • Joins come from ontology relations, and any row limits go into every WHERE.
In the example 
SELECT COUNT(*)                                                   -- the number of deals
FROM s_4a1cb2ceb8871c88."deals" t0                                -- the frozen snapshot
WHERE COALESCE(t0."deal_category" = 'Assisted / failed-bank deal' -- is_assisted_failed, from the ontology
           AND 1980 - t0."year" <= 0                             -- 1980 <= year, written as a difference
           AND t0."year" - 1989 <= 0, FALSE)                     -- year <= 1989
7

Compute in the lake

Data lake

DuckDB runs the SQL inside the data lake. This is where every number in the answer is calculated.

  • Counts first: how many rows the user can see, and how many pass the filter.
  • Then the totals, all in one pass over the data.
  • Then evidence: 8 example rows for people to look at. They are marked as row data and never sent to the LLM.

8

Prove with Z3

Z3

Z3 checks that the answer is the only value possible. How it does that depends on the kind of question.

  • A number: Z3 is told “answer = the exact number from the lake”, then asked “could the answer be anything else?”. It replies unsat, meaning impossible. That is the proof.
  • A table: each cell is proved the same way.
  • Top or bottom: for each rank, a query counts the rows strictly better. The count must match the candidates, so nothing outside the ranking beats it.
  • A yes/no claim about rows: a query searches every row for one that breaks the claim. None found means it holds on this snapshot.
  • Questions with unknowns (“what is the best value?”, “is this possible?”): Z3 solves for the unknowns, with one rule per row. Up to 5,000 rows it sees every row at once; above that it works in rounds (refinement). Your tables have 955 and 510 rows, so Z3 always sees every row.
In the example 
(declare-fun ans () Real)            ; an unknown called ans
(assert (= ans (to_real 132)))       ; ans equals the lake's count
(assert (distinct (to_real 132) ans)) ; ...and ans is something else?
→ unsat: no other value is possible
A question with an unknown: the cost JPMorgan could absorb

“What is the largest extra quarterly cost JPMorgan could have absorbed in every quarter since 2010?” The model uses the approved history window ss_jpm_since_2010 (66 real quarters from the FDIC data) and one unknown, cost_B. Each quarter gives Z3 one rule: pre-tax income minus the cost (scaled by that quarter's assets against today's $4.09 trillion) must stay at or above zero.

Quarters Z3 sawBest cost per quarterDeciding quarterQuarters that break it
66$2.968165 billionQ1 2020: $1.95B pre-tax on $2.69T assets0

Two final proofs follow: no larger cost satisfies every quarter (unsat), and $2.968165 billion is actually reachable. The exact answer is the fraction 81548095599633 / 27474250000000, never rounded inside the proof.

9

Re-check with Lean

Lean

Z3 is fast, but its “unsat” has to be trusted. Lean, a proof checker with a small trusted core, re-checks what Z3 decided using exactly the same formulas.

  • neo writes Z3's conclusions as Lean theorems in a new file for this run.
  • Facts about numbers are checked by Lean's core recomputing the exact fractions itself (decide +kernel). If Lean disagrees with Z3, the run goes to human review.
  • Facts “for every value”, such as “no larger cut is allowed”, are proved by Lean's automatic prover (grind) from only the rows that decide the answer.
  • General theorems in lean/Neo, proved once for all runs (21 of them), explain why a result checked on some rows holds for every row.
In the example

1 theorem: 132 is exactly what the lake's count gives. checked in 2.0 s. It relies on the library theorems unique_of_unsat, sum_const_den and cmp_sign.

For the cost question, Lean checked 4 theorems with 69 facts: the optimum satisfies all 66 quarters, and the key one says that for every possible cost, the Q1 2020 quarter alone forces it to be at most $2.968165 billion.

If Lean is not installed, or lean.enabled is off, this step is skipped and the certificate does not mention it.

10

Recompute another way

Code

A second, separate program recomputes the answer from the raw columns, without the SQL compiler. The two results must agree.

  • Up to 300,000 rows: Python reads the raw columns of the same snapshot and evaluates the model with exact fractions.
  • Above that: a separate floating-point SQL version is used. It is approximate, and the certificate says so.
  • If they disagree, the status becomes mismatch: the answer is marked NOT proved and sent to human review.

Phase 4

Explain and deliver

The LLM double-checks its own reading of the question, code writes down the facts, and the LLM turns those facts into an answer.

11

Review the model

LLM

Claude re-reads its model next to a summary of the result, and either approves it or proposes a fix.

  • What Claude sees: its model and a summary (the answer, row counts, checks). No rows, and no Z3 or Lean files.
  • What it asks itself: Is this the exact question? The right columns for each term? Units converted? No double counting? Is the result plausible? A zero, for example, may mean a misspelled category.
  • Its reply: “ok”, or “revise” with a corrected model. A revised model goes through steps 5 to 10 again, and replaces the original only if it passes.
In the example

Verdict: ok.

Saved: steps/review.json.

12

Write the certificate

Code

Code writes the proof certificate: the complete record of what was asked, how it was computed and how it was proved.

  • The question, the interpretation, the form, the status, and how many rows were used out of how many visible.
  • The result and its exact values.
  • The model: table, joins, filters, definitions, and which numbers were stated rather than taken from data.
  • Each rule applied or not applicable, with the reason.
  • Every check and its result, including Z3, Lean and the independent recomputation.
  • Caveats: missing values skipped, row limits applied, approximations.
  • Where it came from: snapshot, ontology version, rules cited, the LLM used, the user and the run id.

Two copies are made: the full one for people, and one for the LLM with row-level evidence removed.

Saved: certificate.md.

13

Write the answer

LLM

Claude writes the answer for a business reader, using only facts and numbers from the certificate.

  • Answer: one or two sentences, with units and the time window.
  • How it was worked out: 2 to 5 lines in plain words.
  • Proof: what was proved, and whether the independent check matched. A mismatch must be stated as “not proved, under review”.
  • Scenarios (when used): history shares as counts and percentages, with the window named.
  • Caveats: missing values, row limits, assumptions.
In the example

No API key was set when this run was made, so this step used a placeholder text. Every number above was still computed and proved. With Claude connected, this step writes the answer from the certificate.

Saved: answer.md.

14

Route for review

Code

Code decides whether a person must look at the answer before it is trusted.

A run goes to the review queue when any of these is true:

  • The status is not a proof (failed, mismatch, not unique, and so on).
  • The independent check disagreed, or was only approximate.
  • Some totals were computed in floating point.
  • Lean rejected a fact that Z3 reported.
  • A backtest contradicts real past events.
  • The table belongs to a high-impact area (regulatory, board).
  • 4 or more enforced rules shaped the model.
In the example

No reasons, so the answer was delivered straight away. Admin is the only user who can approve reviews.

15

Save and audit

Code

Everything is written to disk, so the run can be inspected, replayed and audited later.

File in var/runs/<run id>/What it holds
model.jsonThe final model
proof.jsonAll SQL with timings, what Z3 was given, solving rounds, the Lean file and its results
certificate.mdThe proof certificate
answer.mdThe answer with the certificate
trace.jsonHow long each step took
steps/, attempts/Each step's output and every model the LLM tried
  • Audit log: “answer delivered”, with user, status, snapshot and tables used.
  • Replay: re-runs the saved model on the same snapshot and ontology and confirms the same answer.
  • Replay on today's data: the same model on the latest data and ontology.
  • Feedback: a thumbs up or down with a comment, stored with the run.

Reference

How a run can end

StatusWhat it means
provedA number, table, ranking or list, proved and independently matched
optimalThe best value was found, nothing better is allowed, and it is reachable
feasible infeasibleIt is possible (with an example), or impossible (with the rules that clash)
refutedA claim was checked and is false, with counterexamples
unboundedThere is no best value: it can grow without limit
undefinedNo eligible row had a value
not_expressibleThe data cannot answer this, and the LLM says so
needs_clarificationThe question could not be linked to any table (step 2)
needs_approvalThe query is too large for the user (step 5)
mismatchThe independent recomputation disagreed: not proved, sent for review
no_modelNo valid model after 4 attempts, so no answer is given
llm_errorThe language model could not be reached or failed
Reference

Words used here

Ontology
The company's dictionary of its data: what each table and column means, in which unit, and which rules apply.
Term
A business word with a definition, such as failed-bank deal or deal year. Columns are linked to terms.
Entity
A kind of thing with its own table: a deal (jp_morgan.csv) or a bank quarter (FDIC history).
Constraint
A business rule in the ontology. “Block” rules must be addressed by the model; “info” rules are background.
Snapshot
A frozen version of every table, so a run always reads the same data.
Briefing
The short extract of the ontology the LLM reads for one question. It has no data rows.
Model
The LLM's precise version of the question: which rows, which formula, which kind of answer.
Form
The kind of answer: value, table, extremum, set, check, feasibility, optimisation, or not expressible.
Grounding
The part of the model that cites the terms used and says how each enforced rule was handled.
Row limit (row policy)
A filter added by code for users who may see only some rows. Admin has none.
Exact fraction
A number kept as a whole-number top and bottom, so nothing is ever rounded.
Z3
A solver. “Unsat” means no value can satisfy what it was asked, which is how a proof is phrased.
Refinement
Solving on a small set of rows, checking the result against every row in the lake, adding the rows that break it, and repeating.
Lean
A proof checker. Its small core re-checks Z3's conclusions; a library of general theorems covers the step from some rows to every row.
Certificate
The code-written record of the question, model, result, checks and sources. The final answer may use only these facts.
